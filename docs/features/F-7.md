## 概要(3行以内)

ノート保存時(memo 作成・screenshot AI 解析完了・ノート更新)に埋め込みベクトルを非同期生成し、notes テーブルへ保存する。
保存済み埋め込みを使って意味的に近い過去ノートを探索し、ノート詳細画面に「類似ノート」として提示する。
関係の種類・説明・エッジ永続化(F-19)、埋め込みのバックフィル・編集時再生成連動(F-21)は本機能(M1-4a)の対象外。

## スコープ / 非スコープ

- スコープ:
  - notes テーブルへの埋め込み関連列追加(`embedding` / `embedding_model` / `embedding_fingerprint` / `enrichment_status`)
  - embedding 生成の非同期ジョブ(キュー `note-enrichment`)と、そのフィンガープリントによる冪等スキップ
  - memo ノート作成直後・screenshot ノートの AI 解析完了直後・ノート更新(PATCH)直後の3経路での enqueue
  - enqueue 失敗時の取りこぼしを回収する定期バッチ `note-enrichment-requeue`(1分間隔。Fable 5 + Codex 独立議論 論点1 で当初の10分から短縮)
  - `GET /notes/:id/related` による類似候補探索(`VEC_DISTANCE_COSINE` フルスキャン、距離昇順最大5件)
  - ノート詳細画面(`NoteDetailPage.tsx`)の「類似ノート」セクション
- 非スコープ(将来拡張の含みも書く):
  - 関係の種類・説明・関連度の AI 判定、ノート間エッジの永続化(F-19。M1-4b で実装)
  - 埋め込み未生成・旧バージョンノートの一括バックフィルジョブ、ノート編集時の埋め込み無効化と再生成の自動連動(F-21。M3)。本機能の「PATCH 時の再 enqueue」は既存ノートを手動再保存で探索対象化する経路の提供であり、F-21 の一括バックフィルの先取りではない
  - 保存直後の独立した類似提示 UI(詳細画面への遷移で F-7 の「保存直後の自動提示」要件を満たす。保存直後専用の別 UI は設けない)
  - 2D/3D ネットワーク描画(F-20。M2)
  - ベクトルインデックスによる検索高速化(数百ノート規模の MVP ではフルスキャンで足りると判断。将来の最適化候補)

## 契約(外部から見える約束)

- **API**:
  - `GET /notes/:id/related` → `{ status: "generating" | "ready" | "failed", similar: RelatedNoteItem[] }`(200)/ `{ message }`(404)。正本スキーマ: `packages/shared/src/contracts/notes.ts`(`notesContract.related` / `relatedNoteItemSchema` / `relatedNotesResponseSchema` / `relatedNotesStatusSchema`)。`status` は DB の `enrichment_status`(pending/completed/failed/NULL)をそのまま返さず、`apps/api` 側の `toRelatedStatus`(`notes.service.ts`)が下表のとおり変換する(Fable 5 + Codex 独立議論 論点2 で確定)。旧仕様(`{ similar: [] }` のみ)では「生成中」と「生成済みだが類似候補なし」を区別できず、埋め込みが非同期生成である以上 UI が永久に空表示のまま固まる問題があった。状態自体を related API に持たせることで、クライアントは related クエリ1本だけをポーリングすればよく、ノート本体クエリとの協調(状態遷移検知後の invalidate)が不要になる。設計原則: NULL を無条件に `generating` へマップしない(解析失敗ノートは enrichment が永遠に始まらず、クライアントのポーリングが止まらなくなるため)。判別不能なケースは必ず終端状態(`ready`/`failed`)へ倒す(ポーリングの fail-safe は「止まる」方向)

    | DB `enrichment_status` | ノートの解析 `status` | API `status` |
    |---|---|---|
    | `pending` | — | `generating` |
    | `completed` | — | `ready` |
    | `failed` | — | `failed` |
    | `NULL` | `pending` / `processing` | `generating` |
    | `NULL` | `failed` | `failed` |
    | `NULL` | `completed` | `ready`(原則発生しない。防御的に終端へ倒す) |
  - 既存 `POST /notes`(memo 作成)・`PATCH /notes/:id`(更新)は変更なしだが、成功時に `note-enrichment` ジョブを追加で enqueue する(レスポンス契約自体は不変)
  - 認可: 既存エンドポイントと同様 `JwtAuthGuard` 必須。404 方針も既存と同じく「対象が存在しない」「他ユーザー所有」を区別しない(`apps/api/src/modules/notes/notes.controller.ts`)
- **DB / データモデル**:
  - notes テーブルへの列追加のみ(別テーブルは作らない。1ノート1埋め込みで JOIN 不要のため)。正本 schema: `packages/db/src/schema/notes.ts`。migration: `packages/db/migrations/0004_add_note_enrichment_columns.sql`
  - 追加列: `embedding` VECTOR(1536) NULL / `embedding_model` varchar(64) NULL / `embedding_fingerprint` varchar(64) NULL / `enrichment_status` enum('pending','completed','failed') NULL(NULL = 対象外・旧データ)
  - データ所有権: `packages/api`(create/update 時に `enrichment_status='pending'` を書き込む)と `packages/worker`(note-enrichment ジョブが embedding 系列を書き戻す)の両方が notes 行を書き込む。両者は後述の CAS(条件付き UPDATE)で競合を調停する
- **ジョブ / イベント**:
  - キュー名: `note-enrichment`。定義の正本: `packages/shared/src/queues/note-enrichment.ts`(payload スキーマ・ジョブオプション・jobId 生成関数を一元定義し、api/worker 双方がこれを import する)
  - payload: `{ noteId: string }` のみ(userId は含めない。処理開始時に DB から実データを再取得して正とする)
  - jobId: `note-enrichment-<noteId>`(ノート単位で決定的)。`attempts: 3`・`backoff: exponential(delay 5000ms)`・`removeOnComplete: true`・`removeOnFail: true`
  - 冪等性: 埋め込み入力(title / summary / body または extracted_text / tags を正規化連結した文字列)の SHA-256 フィンガープリントが保存済み値と一致すれば OpenAI API を呼ばずスキップする(`apps/worker/src/queues/note-enrichment/note-enrichment-fingerprint.ts`)
  - 回収バッチ: `note-enrichment-requeue`(BullMQ repeatable job、1分間隔、`apps/worker/src/queues/note-enrichment-requeue/`。Fable 5 + Codex 独立議論 論点1 で当初の10分から短縮)。`enrichment_status='pending' AND deleted_at IS NULL AND updated_at < NOW() - INTERVAL 1 MINUTE` の行を走査し、対応する BullMQ ジョブが waiting/active/delayed のいずれでもなければ同一 jobId で再投入する
- **画面**:
  - ルート: `/notes/:id`(既存のノート詳細画面 `apps/web/src/pages/NoteDetailPage.tsx` に「類似ノート」セクションを追加。新規ルートは無い)
  - 主要状態: `GET /notes/:id/related` 自身の `status` を条件に、`status === "generating"` の間だけ3秒間隔で条件付きポーリングし、`ready`/`failed` で必ず停止する(Fable 5 + Codex 独立議論 論点2)。生成中(Skeleton)/ 類似なし(`status: "ready"` かつ `similar` が空。「類似するノートはまだありません。」)/ 一覧(`status: "ready"` かつ `similar` あり。各項目はタイトルまたは抜粋、クリックで該当ノート詳細へ遷移)/ 生成失敗(`status: "failed"`。控えめな表示)を区別する。取得自体の通信エラー時は別途「類似ノートの取得に失敗しました。」を表示し、ノート本体の表示は妨げない
  - デザインハンドオフ: 該当なし(計画時点でデザイン不要と判断。既存 shadcn Card/Badge/Skeleton パターンへの追加のみ。`.ai/plans/20260815-m1-4-embedding-relations/m1-4a.md` §デザインとの対応 参照)

## 不変条件・互換性

- 認証必須(既存 `JwtAuthGuard` を継続適用。`GET /notes/:id/related` にも同じガードが付く)
- 既存データとの後方互換: `enrichment_status` は NULL 許容(NULL = 対象外・旧データ)。本機能導入前(migration 0004 時点)に作成された既存ノートは、migration 0005(`packages/db/migrations/0005_backfill_note_enrichment_status.sql`)により2種類に分かれる。**解析成功済み(`status='completed'`)かつ埋め込み入力(title/body/extracted_text のいずれか)を持つ行**は `enrichment_status='pending'` へ是正済みで、回収バッチ(`note-enrichment-requeue`)が拾って埋め込みが生成される。**それ以外の行**(解析失敗等で埋め込み入力が実質空の行)は意図的に是正対象から除外され `enrichment_status` は NULL のまま残る(生成しても入力が空で無意味なため)。この NULL 行は `embedding IS NOT NULL` 条件で類似検索の対象から自然に除外され、related API の status マッピングでは終端状態(`ready`/`failed`)へ倒れるため UI のポーリングも正しく停止する。当面は手動再保存(PATCH)による再 enqueue で探索対象に加わる(一括バックフィル機能自体は F-21)
- 削除時のカスケード方針: 論理削除されたノート(`deleted_at IS NOT NULL`)は、類似検索の対象(自ノート・候補ノートどちらの側でも)から常に除外する。回収バッチも `deleted_at IS NULL` を条件に含み、論理削除済みノートを再投入しない
- embedding 列(raw VECTOR バイナリ)を一覧・詳細・解析処理等の既存レスポンス/クエリへ混入させない。Drizzle の customType で `data`/`driverData` を `never` にしてクエリビルダ経由の読み書きを型エラーにしているが、`select().from(notes)` 等の全列選択は実行時には embedding 列を含む SQL を発行してしまうため、notes を参照する既存クエリは明示的な列投影(`NOTE_COLUMNS`、`apps/api/src/modules/notes/notes.service.ts`)に統一している
- VECTOR 型への書き込み・距離計算は raw SQL(`sql` テンプレート)経由に限定する(Drizzle のクエリビルダに VECTOR 型の型定義が無いため。ADR-0102 の方針を踏襲)
- ジョブの書き戻しは常に条件付き UPDATE(CAS)で保護し、無条件 UPDATE は行わない(次節「データフロー」参照)
- `findRelated` は必ず status を先に読み、その後に類似検索(ベクトル探索)を実行する(次節「データフロー」参照)。逆順にするとレースにより空結果を `ready` として返し、クライアントがポーリングを止めたまま空表示に固まる
- 回収バッチ(`note-enrichment-requeue`)の in-flight 判定は `noteEnrichmentJobId(noteId)` が決定的(ノートごとに一意で不変)であることに依存している。jobId に世代やフィンガープリントを含める変更を行うと、この判定(BullMQ 上の既存ジョブの有無を jobId で照会する仕組み)が機能せず重複投入が発生する(将来の変更者向けの非自明な依存関係。`apps/worker/src/queues/note-enrichment-requeue/note-enrichment-requeue.processor.ts` 参照)

## データフロー

1. 契機発生(memo 作成 / screenshot AI 解析完了 / ノート更新)時、API または worker がまず DB へ `enrichment_status='pending'` を書き込み、その後に `note-enrichment` ジョブを enqueue する(fail-closed。enqueue 失敗はログのみで DB を正とする)
2. note-enrichment ジョブは開始時に対象ノートの内容と `updated_at` をスナップショット取得し、埋め込み入力のフィンガープリントを計算する。保存済み fingerprint と一致すれば OpenAI API を呼ばず completed へ、入力が全フィールド空なら embedding を NULL 化して completed へ、それ以外は OpenAI embeddings API(`text-embedding-3-small`)を呼び出す
3. 書き戻しは `WHERE id = :noteId AND updated_at = :スナップショット AND (title/summary/body/extracted_text/tags が <=> でスナップショットと一致)` の条件付き UPDATE で行う。affected rows = 0(処理中に PUT 更新が入った)の場合は何も書かず正常終了し、`pending` のまま回収バッチまたは次回 enqueue が新内容で再処理して最新内容へ収束する
4. OpenAI 呼び出しが最終試行(attempts 3)まで失敗した場合は同じ CAS 条件で `enrichment_status='failed'` を書き込む(ビジネス上は失敗だが BullMQ ジョブ自体は正常終了させ、無限リトライしない)
5. 詳細画面表示時、`GET /notes/:id/related` はまず対象ノートの `enrichment_status`(NULL 時は `status` から補完)を読んで `status`(`generating`/`ready`/`failed`)を確定させ(この読み取り順序が不変条件。前節「不変条件・互換性」参照。逆順にすると embedding 書き込み直前の空結果を `ready` として返すレースが起こる)、`generating` なら空配列を即返す。それ以外は対象ノートの embedding を相関サブクエリで参照し、同一 user_id・`deleted_at IS NULL`・自ノート除外・`embedding IS NOT NULL` の候補を `VEC_DISTANCE_COSINE` 昇順で最大5件取得して `{ status, similar }` として返す

## エラー・セキュリティ

- エラー:
  - OpenAI embeddings API のエラー・タイムアウト(30秒、`AbortController`): このクライアント自身はリトライせず例外を投げ、リトライは呼び出し元の BullMQ `attempts: 3` に一元化する。最終試行失敗時は `enrichment_status='failed'`(CAS 保護)。ノート本体の閲覧・編集は影響を受けない
  - enqueue 失敗(Redis 停止・タイムアウト。3秒でアプリ側デッドライン): ログ記録のみで例外を re-throw しない。呼び出し元の作成・更新処理は成功として完了する。DB 側の `pending` は既に書き込み済みのため回収バッチが取りこぼしを再投入する
  - `GET /notes/:id/related` で対象ノートが存在しない・他ユーザー所有・論理削除済みの場合は 404(既存エンドポイントと同じ方針で区別しない)
  - VEC_FromText へ渡すベクトルの次元数が想定(1536)と異なる場合は DB エラーとなる。OpenAI クライアント側でもレスポンスの次元数を検証し、不一致なら `OpenAiEmbeddingError` を投げて書き込み前に弾く
- セキュリティ:
  - 認可の単位はユーザー単位(既存 `JwtAuthGuard` + `user_id` 絞り込み)。類似検索は同一 `user_id` の候補のみを対象とし、他ユーザーのノートが混入しない
  - `OPENAI_API_KEY` は worker のみが参照する環境変数。他の外部 API キー(claude-vision.client.ts のパターン)と異なり、**起動時 fail-fast は行わず実行時チェック**とする(未設定でも他機能を止めないため)。エラーメッセージに API キー・リクエストボディ(ノート内容)を含めない(`OpenAiEmbeddingError`)
  - 外部送信: 埋め込み生成時にノートの title / summary / body(または extracted_text)/ tags を OpenAI embeddings API へ送信する(既存の Claude API へのスクショ内容送信と同様、外部送信を伴う)

## 設計判断と理由

- **埋め込みを notes の列として格納**(別テーブルにしない): 1ノートにつき埋め込みは常に高々1件で JOIN が不要なため、専用テーブルを作る複雑さを避けた
- **VECTOR 型は raw SQL 専用**: Drizzle ORM に VECTOR 型の組み込みサポートが無いため、customType で `data`/`driverData` を `never` にしてクエリビルダ経由の誤読み書きを型エラーで防ぎ、書き込み(`VEC_FromText`)・距離計算(`VEC_DISTANCE_COSINE`)は raw SQL テンプレートに限定した(ADR-0102 の PoC 結果を踏襲)。ただし `never` 型はあくまで TypeScript 側の防御であり、`select().from(notes)` のような全列選択は実行時に embedding 列を含む SQL を発行してしまうため、notes を参照する既存クエリを明示的な列投影(`NOTE_COLUMNS`)へ統一する対応を別途行った
- **fail-closed の投入順序**: DB への `enrichment_status='pending'` 書き込みを enqueue より先に行うことで、enqueue 自体が失敗しても「処理すべき」という事実が DB に残り、回収バッチが必ず拾える設計にした(enqueue を先にすると、DB 書き込み失敗時にジョブだけが実行されノートが存在しない/古い状態のまま処理される可能性があった)
- **フィンガープリントによる冪等スキップ**: 同一内容で複数回 enqueue されても OpenAI API 呼び出し(課金対象)を重複させないため、入力内容の SHA-256 が変わらない限り API を呼ばない設計にした
- **CAS(条件付き UPDATE)による書き戻し保護**: `updated_at` が秒精度(fsp=0)であり、同一秒内の PUT 更新を `updated_at` 単独では検知できないため、内容列の `<=>`(NULL 安全等価)比較を併用した。affected rows = 0 の場合は何も書かずに正常終了させ、`pending` を維持したまま最新内容へ収束させる設計にした(無条件 UPDATE で新しい `pending` を古い結果で上書きしてしまう不整合を避けるため)。同じ CAS を `failed` の書き込みにも適用している(更新後に再設定された `pending` を `failed` で潰すと回収バッチの対象から外れてしまうため)
- **jobId をノート単位で決定的にし、removeOnComplete/removeOnFail を true にする**: 実行中・待機中(waiting/active/delayed)の間は同一 jobId の重複投入を BullMQ 側で抑止しつつ、完了・最終失敗後は同一 jobId で再投入できるようにした(更新時の再保存・回収バッチの双方が同じ jobId 規則に乗れる)
- **類似検索はベクトルインデックスを使わずフルスキャン**: 数百ノート規模の MVP では `VEC_DISTANCE_COSINE` のフルスキャン + `ORDER BY distance LIMIT 5` で非機能要件(応答性 1〜2秒)に収まると判断し、インデックス化は将来の最適化として先送りした
- **OPENAI_API_KEY は起動時 fail-fast しない**: worker の他機能(screenshot 解析等)がこのキーに依存しないため、未設定であっても worker 全体の起動を止めず、embedding 生成が必要になった時点でのみエラーにする設計にした
- **OpenAI クライアントは公式 SDK を使わず fetch ベースの薄い実装**: 使用するエンドポイントが embeddings の1つのみのため、追加の依存パッケージ導入は見送った
- **related レスポンスへ `status` を追加**(Fable 5 + Codex 独立議論 論点2): 埋め込みは非同期生成のため、旧仕様(`{ similar: [] }` のみ)では「生成中」と「生成済みだが類似候補なし」を空配列として区別できず、UI が永久に空表示のまま固まる問題があった。状態を related API 自身に持たせることで、クライアントは related クエリ1本だけをポーリングすればよく、ノート本体クエリとの協調(状態遷移検知後の invalidate)が不要になる。DB の `enrichment_status` をそのまま公開せず変換するのは、NULL を無条件に `generating` とみなすと解析失敗ノート(enrichment が永遠に始まらない)でポーリングが止まらなくなるため。判別不能なケースは必ず終端状態(`ready`/`failed`)へ倒す(ポーリングの fail-safe は「止まる」方向)
- **`findRelated` は status を先読みしてから類似検索を行う**(Fable 5 + Codex 独立議論 論点2): worker の `writeBackEmbedding` は embedding と `enrichment_status='completed'` を同一 UPDATE で原子的に書くため、「status=completed を観測した時点で embedding は必ず存在する」が保証される。逆順(類似検索を先に読む)だと、embedding 書き込み直前に空の候補を取得した直後に completed になった status を読んでしまい、`ready` + 空を返してクライアントがポーリングを止めたまま固まるレースが起こり得る。また `generating` の場合はベクトル検索自体をスキップして空配列を返す(ポーリング中の無駄なクエリ回避)
- **回収バッチの周期を10分→1分へ短縮**(Fable 5 + Codex 独立議論 論点1): `note-enrichment` の jobId はノート単位で決定的なため、ジョブが active の間にノートが更新されると、新規 enqueue は同一 jobId で BullMQ に抑止され、実行中ジョブの結果も CAS 不成立で破棄される。この結果どのジョブも新内容を処理していない状態になりうるが、元の10分間隔ではこの回収バッチが拾うまで最悪20分程度、埋め込みが古いままだった。周期短縮により最悪ケースは約2分に短縮される(副次効果として API 側の enqueue 失敗からの回復も同様に速くなる)

## 既知の制約・未解決事項

- 既存ノート(本機能導入前に作成されたノート)への埋め込み一括付与を**機能として**(任意のタイミングで全ノートを遡って再生成する仕組みとして)は提供しない。F-21(M3)へ先送り。ただし migration 0005 により、導入時点(migration 0004)の既存行のうち解析成功済みかつ埋め込み入力を持つものは `enrichment_status='pending'` へ是正済みで、回収バッチ経由で手動再保存を待たずに埋め込みが生成される。是正対象外(解析失敗等で埋め込み入力が空)の行のみ、当面は手動でのノート更新(再保存)により個別に探索対象化する必要がある
- ノート編集時の「埋め込みの即時無効化」と「F-19/F-22 の関係再生成への自動連動」は F-21/F-22(M3)の対象。本機能が提供するのは PATCH 時の再 enqueue(fingerprint 変化時のみ再生成)までで、既存エッジとの連動は行わない(関係生成自体が M1-4b 未実装のため連動対象も存在しない)
- ベクトルインデックスを使わないフルスキャン方式のため、ノート数が数百規模を大きく超えた場合の応答性は未検証。将来的な最適化候補として残す
- 上記「テスト観点」節に記載のとおり、統合テスト2件および mariadb 11.8 実機確認(`pnpm poc:vector`)は 2026-08-16 に実施済み(全 green)。ただし `OPENAI_API_KEY` 未設定のため実データでの埋め込み品質確認は引き続き未実施
