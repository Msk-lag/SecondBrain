## 概要(3行以内)

知識ネットワーク全体(ノード=ノート、エッジ=F-19 の確定関係)を、ノート数・エッジ数に依存しない**固定回数の SQL(通常3本。ノード0件時のみエッジ SQL を省いて2本)**で取得する `GET /graph` を新設した。
ネットワーク描画(react-force-graph)が一括入力として使えるレスポンス形へ、DB の a/b 正規化・向き表現をそのまま露出せず変換して返す。

## スコープ / 非スコープ

- スコープ:
  - 契約 `packages/shared/src/contracts/graph.ts`(`GET /graph`)
  - `apps/api/src/modules/graph/`(`graph.service.ts` / `graph.controller.ts` / `graph.module.ts`)
  - 統合テスト `apps/api/test/graph.e2e-spec.ts`
- 非スコープ(将来拡張の含みも書く):
  - **M2-2(web 側の描画・画面一式)**: グラフの実際の描画(react-force-graph)、`GET /graph` のポーリング、上限到達時の打ち切り Alert 表示、孤立ノートの表示制御、次数(接続数)からのノードサイズ算出。本文書は将来 M2-2 の実装時にこれらの節が追記される想定である
  - `GET /notes/:id/related` の変更(**現行契約を一切変えていない**。以下「契約」節参照)

  - エッジの無効化(F-22・M3)

## 契約(外部から見える約束)

- **API**: `GET /graph` → 200 `{ nodes, edges, truncated: { nodes, edges }, processingNoteCount }` / 未認証 401。正本スキーマ: `packages/shared/src/contracts/graph.ts`(`graphNodeSchema` / `graphEdgeSchema` / `graphResponseSchema` / `graphContract`)

  **エッジの向きの変換表**(契約の中核。DB の `type_direction` から `source`/`target`/`directed` への変換):

  | DB `type_direction` | `source` | `target` | `directed` |
  |---|---|---|---|
  | `a-to-b` | `note_a_id` | `note_b_id` | `true` |
  | `b-to-a` | `note_b_id` | `note_a_id` | `true` |
  | `none` | `note_a_id` | `note_b_id` | `false` |

  読みは常に「`source` →(関係の種類の左項→右項)→ `target`」(例: `cause-solution` なら `source` が原因側)。**a/b を露出しない理由**: ネットワーク全体には「閲覧中のノート」という視点が存在せず、DB の a/b 基準(正規化上の役割)も既存 `GET /notes/:id/related` の `typeDirection`(閲覧ノート視点)もそのままでは使えない。`{ source, target }` というキー名は react-force-graph の `links` が既定で読むプロパティ名と一致しており、web 側での詰め替えを不要にする

  - `bodyPreview` = `LEFT(body, 120)`。**タイトル未入力時のラベル補完専用**であり、web の既存 `getDisplayTitle({ title, body })`(タイトル未入力時は本文冒頭30文字)をそのまま再利用でき、一覧・詳細画面とラベルが一致する。ノードは lean に保ち、要約・本文全体・画像は含めない(同時に読むのは常に1件であり、ノード選択時に既存 `GET /notes/:id` / `GET /notes/:id/image` で取得すれば web 側でキャッシュが詳細画面と共有される。全ノードぶんの本文を含めるとペイロードを膨らませるだけである)
  - **`similar`(類似候補)を一切含めない**: F-7 が「ネットワークビューに描画するエッジは F-19 の確定エッジのみ」と定めているため
  - **次数(接続数)は返さない**: 「ノードサイズ = 接続数」に使う次数は返した `edges` 配列から**web 側で数える**。DB 上の次数を返すと、上限で落ちたエッジぶん描画上の次数と食い違う
  - `truncated`(上限到達の表明): 上限は `GRAPH_NODE_LIMIT`(300)/ `GRAPH_EDGE_LIMIT`(900)のハードキャップ。`truncated.nodes` が true のときは上限外ノートへのエッジも表示されないため、**返却されたノードの次数が実際より少なく見える**(上限外ノートと繋がっていたエッジが不可視になるだけで、返却ノード同士のエッジは欠落しない)
  - `processingNoteCount`: 「AI が新しい関係を判定中です(N件)」バッジ表示と、ポーリング間隔の緩急に使う**ヒント**であり、「0 = 全処理完了」の**保証ではない**。捕捉する4条件は次節「データフロー」参照。初回判定対象ノートの埋め込み書き戻し(`enrichment_status='completed'`)から関係判定ステージの claim(`relation_status='pending'`)までの**同一プロセス内・1 UPDATE 分の窓**は捕捉できないが、web がこの値を**ポーリングの停止条件に使わない**設計であるため実害を持たない(バッジが一瞬消えるだけ)
  - **`GET /notes/:id/related` との併存**: `related` は単一ノート視点で確定エッジ(閲覧視点の向き)+ 類似候補 + ノート単位の2状態を返す。`/graph` は全体視点で確定エッジのみ(エッジ自身の向き。閲覧視点が存在しないため)+ ユーザー単位の集計状態(`processingNoteCount`)を返す。詳細画面は類似候補も併記する仕様(F-7)であり `/graph` では代替できず、逆に `/graph` へ `similar` を混ぜると F-7(描画するエッジは F-19 の確定エッジのみ)に反する。投影列も向きの表現も異なるため SQL の共通化は行わない。**related の契約自体は本ユニットで変更していない**
- **DB / データモデル**: 変更なし。既存の `notes` / `note_relations` テーブルをそのまま読む(理由は「設計判断と理由」節)
- **ジョブ / イベント**: なし(`/graph` は読み取り専用で、ジョブを起動・消費しない)
- **画面**: 該当なし(M2-2 のスコープ)

## 不変条件・互換性

- 認証必須(既存 `JwtAuthGuard` を継続適用)
- `GET /notes/:id/related` のレスポンス契約は不変(受入条件13で回帰確認済み)
- notes を参照するクエリは embedding(raw VECTOR)を絶対に SELECT しない。明示列投影の raw SQL に統一している(F-7 / PROJECT.md / M1-4a D0 指摘[4] の規律を継続)
- エッジは常に「返却ノード集合の誘導部分グラフ」(両端が返却ノード ID 集合に含まれるエッジ)に絞ってから上限を適用する。順序を逆にすると上限外ノートの高関連度エッジが枠を占有し、返却ノード同士のエッジが DB にあるのに落ちて疎なグラフになる
- 孤立ノート(確定エッジを一切持たないノート)を API では除外しない。ノード=ノートという F-20 の定義に反するため

## データフロー

1. `JwtAuthGuard` でユーザーを解決し、`GraphService.findGraph(userId)` を単一トランザクション内で呼ぶ
2. (1) 処理中件数 → (2) ノード(`created_at DESC, id DESC` で上限+1件取得し超過分を切り詰め、新しいノートを優先)→ (3) エッジ(切り詰め後のノード ID 集合を WHERE に渡し、両端がその集合に含まれるエッジのみを `relatedness DESC, id ASC` で上限+1件取得し切り詰め)の順で実行する。ノード0件の場合は空 `IN ()` の構文エラーを避けるためエッジ SQL 自体を発行しない(この場合のみ SQL は2本)
3. `processingNoteCount` は未削除ノートのうち次の4条件のいずれかに一致する件数: (a) `status IN ('pending','processing')`(スクショ解析中)/ (b) `enrichment_status = 'pending'`(埋め込み待ち・実行中)/ (c) `relation_status = 'pending'`(関係判定中)/ (d) `enrichment_status = 'completed'` かつ `relation_fingerprint IS NOT NULL` かつ `relation_fingerprint <> embedding_fingerprint`(内容更新後の再判定待ち。`relation_fingerprint IS NULL` の行〔M1-4a 期の既存ノート〕は数えない)
4. エッジの向きは `toGraphEdgeEndpoints`(純関数)で `type_direction` を「契約」節の変換表どおり `source`/`target`/`directed` へ正規化する
5. レスポンスを組み立てて返す

## エラー・セキュリティ

- エラー:
  - 未認証: 401(`JwtAuthGuard`)
  - `/graph` 自体に新規のエラー経路(404 等)は無い。ユーザーのノートが0件でも空配列 + `processingNoteCount: 0` を正常応答として返す
- セキュリティ:
  - 認可の単位はユーザー単位。3クエリすべてが `user_id` で絞られ、加えてエッジ SQL は `nr.user_id` に加え**ノード ID 集合自体がユーザー一致・未削除で絞り込み済み**であることで両端の所有者一致を担保する(多重防御。`nr.user_id` は一致するが端点ノートの一方が他ユーザー所有、という不整合データが混入しても誘導部分グラフの外側に落ちて自然に除外される。統合テストで確認)
  - レート制限: `UploadRateLimitGuard` は付けない(AI 課金経路の予算を守るためのガードであり、`/graph` は外部 API を呼ばない読み取り専用エンドポイントのため対象外)。読み取り系エンドポイント全般への一般的なレート制限は別 Issue(#65)の担当範囲
  - 外部送信: なし

## 設計判断と理由

- **エンドポイントを `/notes/graph` ではなく独立した `GET /graph` にした**: `/notes/graph` は既存 `GET /notes/:id` と経路が衝突し、Express の登録順に依存して `:id` 側が先に一致すると 404 になりうる。ts-rest/nest は契約側から登録順序を保証できないため、衝突しないパスを選んで問題自体を消した
- **エッジは「返却ノード集合の誘導部分グラフ」に絞ってから上限を適用する**(順序を先にエッジ全体の切り詰め→端点フィルタとしない): 順序が逆だと上限外の古いノートの高関連度エッジが 900 枠を占有し、返却ノード同士のエッジが DB にあるのに落ちて疎なグラフになる。この順序にしたことで、エッジ SQL から `notes` JOIN も不要になった(ノード ID 集合による WHERE 絞り込みだけで両端の所有者一致まで担保できるため)
- **ページングを採用しない**: 力学レイアウトはグラフ全体を入力とする一括計算であり、部分集合を渡すとレイアウトが別物になる。ページを跨ぐたび配置が変わり「ネットワークを眺める」体験が成立しない。本プロジェクト標準のカーソルページネーションも順序のある一覧が前提であり、グラフには対応しない。上限は「取得を分割する仕組み」ではなく「描画性能を守る安全弁」である。将来スケール時の発展方向は近傍 N ホップの部分グラフ抽出(F-12/F-13 の領域)
- **SQL は単一トランザクションの一貫スナップショットで読む**(実行順は「件数→ノード→エッジ」): 独立したクエリのままだと、エッジ取得後・件数取得前に worker が関係をコミットした場合に「古いエッジ + `processingNoteCount: 0`」という**自己矛盾したレスポンス**(グラフには写っていない関係を、進行状況は「完了」と表明している状態)が成立しうる。同一スナップショットで読めば「件数が0ならその時点で確定済みのエッジはすべて `edges` に入っている」ことが保証され、グラフと進行状況ヒントが常に整合する。MariaDB/InnoDB の REPEATABLE READ は同一トランザクション内の最初の一貫読み取りでスナップショットを確立するため、`db.transaction()` の内側で実行すれば同一スナップショットで読める。実行順を件数から始めるのは、万一この一貫性が構成上効かない場合でも、`processingNoteCount` がグラフより新しくなる(実際より処理が進んで見える)側ではなく、新しくならない側へ倒すため

  **注意(M2-2 実装者向け)**: この判断の当初の動機は「`processingNoteCount: 0` を見た web がポーリングを止め、古いグラフのまま固まる」ことの防止だったが、その後の設計変更で **web は `processingNoteCount` をポーリングの停止条件に使わない**ことが確定した(§契約 参照)。したがって本トランザクションは**正しさの必須条件ではなく、レスポンスの自己整合性を保つための多重防御**である(害が無くコストも小さいため実装を残した)。**「件数が0になったらポーリングを止める」という実装をしてはならない。**
- **ノード0件のときエッジ SQL を発行しない**: 空の `IN ()` は MariaDB の構文エラーになるため
- **孤立ノートを API では除外しない**: ノード=ノートという F-20 の定義に反するため。M1-4a 期のノートは `relation_status` が NULL のままで孤立ノードが多数存在する前提だが、既定表示で隠すかどうかは M2-2 の表示制御の責務とする
- **DB スキーマ変更・migration は不要と判断した**: ノード取得は既存の複合索引 `notes_user_id_created_at_id_idx`(`user_id, created_at, id`)が効き、エッジ取得は `UNIQUE (user_id, note_a_id, note_b_id)` の `user_id` 前置で絞れる(`relatedness DESC` の filesort は 900 件規模で問題にならない)
- **上限値を 300ノード / 900エッジに決めた根拠**: 要件 §5「MVP は2D表示で数百ノート規模で操作可能な fps を保つ」を満たしつつ、関係判定の候補は1保存あたり5件上限(`RELATION_CANDIDATES_LIMIT`)であり `note_a_id < note_b_id` への正規化によりエッジ数はノート数の2〜3倍に収束する見積もりから、エッジ上限をノード上限の3倍とした。初版はそれぞれ500/1500だったが、Fable 5 + Codex 独立議論で「未検証の上限は小さい側が安全」と判断し300/900へ引き下げた(要件の「数百ノート」は満たしたまま。上限を引き上げる場合は定数1行の変更で足りる)

## 既知の制約・未解決事項

- 上限規模(300ノード / 900エッジ)での応答性の実測は未実施(実データ投入スクリプトは M2-2 のスコープ)。統合テストで観測できるのは小規模フィクスチャでの実行時間のみで、M2-1 の実装時点では 1リクエストあたり 10〜23ms(接続あたりの `max_statement_time = 8` 秒に対して十分小さい)
- 上限到達時、孤立ノートが新しく接続ノードが古いと、接続ノードが先に切り捨てられうる(実データ規模では発生しない既知の制約)
- エッジの単調追加による陳腐化: 候補外・`related=false` になった既存エッジは無効化されない(F-22・M3)ため「もう関係が無いはずのエッジ」が残りうる。graph API はこれを補正しない(API 側で隠すと詳細画面と表示が食い違うため)
- `IN` 句のバインド数は最大1000個。ノード上限を将来引き上げる場合は、誘導部分グラフを派生テーブルで表現する方式への切り替えが必要になる
