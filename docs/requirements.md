## 1. 目的・コンセプト

**「脳みその中の自分の知識を、そのまま外部に可視化する」** ナレッジベースアプリ。

Obsidian のようなナレッジベースは「メモを手で書く行為自体が面倒で続かない」。
そこで「書く」のではなく **「貼るだけ」** で知識が溜まり、AI が要約・タグ付け・関連付け・階層化を肩代わりする形に転換する。

このコンセプトの到達点が **3D 脳ビュー(§2.2)** — 溜まった知識が球体のネットワークとして立体的に可視化され、文字通り「自分の脳を外から眺める」体験である。

脳のアナロジーを設計思想とする:

| 脳の働き | アプリでの対応 |
|---|---|
| 連想記憶 | 保存した瞬間に意味的に近い過去ノートを自動提示 |
| 記憶の風化と強化 | 使われないノートは背景に退き、よく参照するノートは目立つ |
| フォルダではなくネットワーク | 手動整理を強制せず、意味的な繋がりで自動構造化 |
| 概念の階層(抽象→具体) | 知識量に応じて自動で深くなる階層型知識マップ(DB → PostgreSQL → 個別ノウハウ) |
| 睡眠中の記憶整理 | バッチ処理で過去ノート同士を見直し、新しい繋がりを提案 |

## 2. 完成系ビジョン(合意済み)

完成した SecondBrain で **できること** を先に定義し、そこから逆算して開発する。

### 2.1 日常の体験

1. **貼って忘れる** — 気になった記事の URL やスクショを貼るだけで終わり。数十秒後には要約・タグ・キーワード付きのノートになっている
2. **ノートだけで読める** — 要約は詳しく、**本文もアーカイブされている**ため、元記事が消えても(リンク切れでも)自分の知識として成立する。元 URL への導線も残る
3. **保存した瞬間の気づき** — 保存直後に関連する過去ノートが提示され、「前にも似たものを保存していた」ことに気づく
4. **トピックでたどる** — 「PostgreSQL」等のエンティティをクリックすると、情報源を問わず関連知識が1ページに集約される(Postgres/ポスグレの表記ゆれも吸収)
5. **あいまいに思い出す** — 「あの時保存してた引っ越しの記事」と**検索ボックスに自然文で打つ**と該当ノートが見つかる(チャット型の対話 UI ではない)
6. **忘れた頃の再会** — アプリを開くとホームに「今週のダイジェスト」「しばらく見ていないノート」が浮上する

### 2.2 3D 脳ビュー(いちばんやりたいこと・完成系の中心)

自分の知識全体が **3D 空間の球体ネットワーク** として表示される画面。

- **球体 = 知識の階層ノード**。大きな球体は抽象的な領域(例: DB)、その下に中くらいの球体(例: PostgreSQL / Oracle)、さらに細かい粒度の情報へ…と階層的に繋がる。**階層は固定ではなく、貯めた情報の量に応じて自動で深く・細かくなっていく**
- **球体のサイズ = 情報量**。紐づく知識が多いほど球体は大きい。よく参照する領域は目立ち、使われない領域は背景に退く(風化と強化)
- **線 = 意味的な繋がり**。球体同士が線で結ばれネットワークを形成する。3D 空間を回転・ズーム・ドリルダウンして眺められる
- **線を選択 → 決定すると、その繋がりの「関連する情報の要約」が出る**。両端にまたがるノート群を根拠に、Claude が「この2つはこう繋がっている」という説明をその場で生成する(生成結果はキャッシュし再利用)
- **その要約をもとに NotebookLM 用プロンプトを出力できる**。選択した繋がりに含まれるノート本文・出典 URL・関係要約を、NotebookLM に貼り付けられる形式(Markdown/プロンプト文)に整形してコピー/ダウンロードできる

### 2.3 その他の完成系要素

- **身内も使っている** — 家族・友人が自分のアカウントで同じ体験をしている(AWS 上で稼働、データ分離、API 利用量上限で保護)
- **裏で記憶が整理される** — バッチ処理が過去ノート同士を見直し、新しい繋がりを提案してくる(努力目標)

### 2.4 完成の定義

**「構想の全機能が揃ったこと」を完成とする**(利用定着や公開規模ではなく機能完成主義)。具体的には:

- [ ] 貼るだけ知識化(URL / スクショ / 手動メモ、本文アーカイブ込み)
- [ ] 関連ノートの自動提示
- [ ] 自然文での想起(検索ボックス型)
- [ ] 忘れた頃の再浮上(ホーム表示・ダイジェスト・風化と強化)
- [ ] エンティティページ(表記ゆれ吸収込み)
- [ ] **3D 脳ビュー**(自動階層化・球体サイズ=情報量・線の選択→AI 関係要約・NotebookLM プロンプト出力、まで含めて一式)
- [ ] 身内公開(認証・利用量上限・AWS 本番稼働)

バッチによる繋がり提案(§2.3)は完成の必須条件には含めず、努力目標(Could)とする。

## 3. 利用者・利用環境(決定事項)

| 項目 | 決定 |
|---|---|
| 利用者 | 当面は開発者本人。**近い将来に身内へ公開**する前提でマルチユーザー設計にする |
| 入力経路 | **PC ブラウザの Web 画面**(保存フォームに URL / スクリーンショットを貼る)。ブラウザ拡張・スマホ共有は将来検討 |
| 稼働環境 | **AWS(コスト考慮により EC2 + RDS のみ使用)**。EC2 1台に Docker Compose でアプリ一式(web / api / worker / Redis / MinIO)、DB は RDS。開発中はローカル(Docker)で動かし、本番とローカルで同じ構成を保つ。※通常はローカル運用とし、AWS 公開は提出・レビュー等の期間限定(終了後はスナップショット退避して撤収)。常時稼働は M7(身内公開)実施時のオプション |
| 再浮上の届け方 | **アプリを開いたときのホーム表示(プル型)**。メール等のプッシュ通知はスコープ外(将来検討) |
| ノートの役割 | **ノート内で完結して読める**(索引ではなく読む場所。本文アーカイブでリンク切れに耐える) |
| 想起 UI | **検索ボックス型**(チャット型 RAG はスコープ外) |
| 脳ビューの構造 | **階層型**(抽象領域 → 具体トピック → 細粒度、情報量に応じて階層が自動で深くなる)。**3D 表示は必須要件** |
| 線の要約 | **AI がその場で生成**(初回生成 → キャッシュ)。既存要約の一覧表示では代替しない |
| AI 基盤 | Claude API(要約・タグ抽出・マルチモーダル画像入力・関係要約)。API コストは開発者負担、身内公開時は利用量上限で保護 |

| F-15 | **NotebookLM 用プロンプト出力**: 選択した繋がり(またはトピック)に含まれるノート本文・出典 URL・関係要約(F-14)を、NotebookLM に貼り付けられる Markdown/プロンプト形式に整形してコピー/ダウンロードできる(NotebookLM に個人向け API は無いため手動貼り付け前提) | Must | M6 |
| F-16 | バッチ処理で過去ノート同士の新しい繋がりを提案する(「睡眠中の記憶整理」) | Could | 任意 |

## 5. 非機能要件

| 分類 | 要件 |
|---|---|
| 応答性 | 保存操作の受付は即時(目標 1 秒以内)。要約・埋め込み生成は非同期で数十秒許容。一覧・検索は体感ストレスのない速度(目安 1〜2 秒) |
| 3D 描画 | WebGL 前提。数千ノート規模でも階層による集約表示(上位階層のみ描画しドリルダウンで展開)により操作可能な fps を保つ。PC の一般的な GPU で動くこと |
| 生成コスト | 繋がりの AI 要約(F-14)はキャッシュ必須。同一の繋がりに対する再生成は根拠ノートが変化した場合のみ。階層マップ再構築(F-12)はバッチで、保存のたびに全再計算しない |
| コスト | 個人負担で維持できること。目安: AWS + Claude API 合算で月数十ドル以内(公開後に見直し)。インフラは小さく始めてスケールは追わない |
| ストレージ | 本文アーカイブ・スクショ画像は S3 互換 API(MinIO)経由で保存する。ローカル・本番(EC2 上のコンテナ+EBS)とも MinIO で統一し、将来 S3 へ移行する場合も接続先変更のみで済む設計とする |
| セキュリティ | Claude API キーはサーバー側のみに置きクライアントへ出さない。秘密情報は環境変数(`.env` は Git 管理外)。公開時は HTTPS + 認証必須。アーカイブ本文は保存者本人のみ閲覧可(私的複製の範囲に留め、公開・共有機能は設けない) |
| データ保全 | DB は RDS の自動バックアップ、MinIO データ(EBS)は EBS スナップショットで保全する。全ノートのエクスポート手段(F-6)を確保する |
| 可用性 | 個人利用レベル。計画停止・多少のダウンは許容 |
| 対応環境 | PC のモダンブラウザ(Chrome 最新を基準)。スマホは閲覧がベストエフォート(3D 脳ビューは PC 専用でよい) |
| 可搬性 | ローカル(Docker Compose)と AWS の両方で動くこと。環境差は環境変数で吸収する |

## 6. 制約・前提

- DB は MariaDB(ネイティブベクトル対応版、11.7 以降)。F-7/F-8/F-12 のベクトル検索は MariaDB の VECTOR 型+ベクトルインデックスで実現し、品質・マネージド対応(RDS のバージョン提供状況)に問題が出た場合のみ Qdrant をベクトル専用ストアとして併用する(M0 で技術検証)。階層・エッジは再帰 CTE+エッジテーブル、日本語全文検索は InnoDB ngram パーサで実現する
- LLM は Claude API を使用(マルチモーダル要件 F-2、関係要約 F-14 のため)
- Web スクレイピング/本文抽出が必要(F-1)。取得先サイトへの負荷・利用規約に配慮し、リトライは控えめにする。本文アーカイブは私的利用の範囲に留める
- NotebookLM 連携は手動貼り付け(個人向け公式 API が存在しないため)
- 開発は本リポジトリの開発ハーネス(手動モード `/dev-cycle` から開始)で行う

## 8. スコープ外(明示)

- **チャット型の想起 UI(RAG で回答を合成する対話形式)** — 完成系は検索ボックス型と決定。将来の拡張余地としては残す
- ブラウザ拡張・スマホ共有シートからの保存(将来検討)
- メール/プッシュ通知による再浮上(プル型のみ)
- 手書きの長文ノート作成体験(Obsidian の代替はしない — 「貼るだけ」が主役)
- 収益化・不特定多数への公開(身内まで)
- アーカイブ本文の共有・公開機能(著作権配慮のため本人閲覧のみ)
- NotebookLM への自動アップロード(API が無いため手動貼り付けまで)

## 9. 技術スタック(決定記録)

**決定(2026-07-07)**: **TypeScript 統一**(バックエンド: Node.js / フロントエンド: React + WebGL)。

**選定理由**(学習コストを除いた保守性・運用性・開発継続性の比較で決定):
- フロントは 3D 脳ビュー(Three.js 系)の都合で React + TypeScript がほぼ確定しており、バックエンドを揃えると型をフロント・バックで共有でき、API 境界の追従漏れをコンパイル時に検出できる(保守性)
- ランタイムが軽く(JVM 比)、Dockerfile・CI・依存管理が1系統で済み、月数十ドル以内のコスト要件に適合(運用性)
- 1機能=「画面+API+ジョブ」を単一言語・単一ツールチェーン(`npm test` / lint 一本)で縦に貫通でき、ハーネスで1機能ずつ回す開発スタイルと相性が最良(開発継続性)
- 重要部品がすべて JS 圏にホームを持つ: 本文抽出 = Mozilla Readability 本家 / Claude 公式 SDK(TS が最も手厚い)/ 非同期ジョブ = BullMQ / 3D = Three.js
- 比較検討した代替案: Spring Boot(既習だが2言語体制の保守・運用コストで劣後)/ Python(クラスタリングは最強だが型と統一性で劣後。F-12 が重くなったら Python ワーカー切り出しの補欠起用余地を残す)/ Go・Rust(このドメインでエコシステムが薄く見送り)

**確定要素**: TypeScript / Node.js / React / MariaDB(ネイティブベクトル。必要時のみ Qdrant 併用 — §6)/ Docker Compose(ローカル)/ AWS は **EC2 + RDS のみ**(EC2 1台に Docker Compose 一式、コスト考慮の決定)/ オブジェクトストレージは MinIO(S3 互換 API、ローカル・本番共通)/ Claude API(公式 TS SDK)

**アプリ構成の決定(2026-07-07)**: **分離型** — Vite + React SPA(web)/ NestJS API(api)/ BullMQ ワーカー(worker)のモノレポ構成。

分離型を選んだ理由(「アプリの目的への適合」で判断):
- 完成系の中心である 3D 脳ビューは SSR 不要の純クライアントアプリであり、Vite SPA なら Three.js 系を回避策なしで扱え、最重要画面の試行錯誤が最速になる(Next.js は `ssr: false` ラップとサーバー/クライアント境界の管理を主要画面で引きずる)
- 裏の主役である AI パイプライン(要約→埋め込み→階層化→関係要約)は、NestJS の BullMQ 統合・スケジューラ・モジュール構造が公式装備で、ジョブの増築に秩序を与える
- M4 以降複雑化するドメイン(ノート・エンティティ・階層・繋がり・要約キャッシュ)に対し、NestJS の強制的な構造規律が保守性に効く
- 型の端から端までの共有は tRPC(スタンドアロンアダプタ)または ts-rest で分離型でも実現できる(方式は M0 で確定)

**M0 で決める詳細**: ORM(Drizzle / Prisma)/ 型共有方式(tRPC / ts-rest / 共有 DTO)/ 認証ライブラリ / モノレポツール(pnpm workspaces 等)/ テスト・lint ツールチェーン / フロント詳細(3D グラフライブラリ = react-force-graph-3d 起点を想定、サーバー状態 = TanStack Query、クライアント状態 = Zustand、UI = Tailwind + shadcn/ui、ルーティング = React Router を想定)
