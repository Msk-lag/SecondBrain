## 1. 目的・コンセプト

**「スクリーンショットを貼るだけで、AI が知識ネットワークを育てる」** 個人向けナレッジアプリ。

目指す体験に最も近い既存サービスは **TheBrain** である。ただし TheBrain はユーザーが知識ノード・ノード間の関係を手動で作成していくのに対し、SecondBrain はその知識ネットワーク構築を **AI が自動化する** 点が本質的な違いである。

**解決したい課題**:
- 保存しただけで見返さない
- どこに保存したか分からなくなる
- 内容をノートに整理するのが面倒
- 過去に保存した情報との関係に気付けない
- 知識管理ツールは手作業が多い
- 「保存する行為」と「知識として活用する行為」が分断されている

**AI が自動で行うこと**:
1. スクショの内容を読み取る
2. 知識として要約する
3. キーワード・概念・技術・人物・商品などを抽出する
4. 過去の知識との関連を探す
5. 関係の種類と理由を生成する
6. 知識ネットワークへ自動追加する

SecondBrain は単なるスクショ管理アプリ・OCR アプリ・AI 要約アプリではない。他との差別化点は **AI が自動構築した知識ネットワークをインタラクティブに探索できること**(MVP は 2D 表示。3D 化はストレッチ — §2.2)にある。

脳のアナロジーを設計思想とする(現行分):

| 脳の働き | アプリでの対応 |
|---|---|
| 連想記憶 | 保存時の関係生成と関連提示 |
| フォルダではなくネットワーク | AI による自動構造化 |

以下は将来構想として設計思想に残すが、MVP のスコープには含まない: 記憶の風化と強化(使われないノートを背景に退かせる表現)/ 概念の階層(抽象→具体の自動階層化)/ 睡眠中の記憶整理(バッチによる繋がり提案)。詳細は §2.3 を参照。

## 2. MVP と将来構想

### 2.1 MVP の体験(コンテスト・ポートフォリオで見せる一連のフロー)

1. SNS 投稿や技術情報のスクショを貼る
2. AI が内容を解析する
3. タイトル・要約・キーワードが生成される
4. 過去の知識との関係が発見される
5. ネットワークビューに新しいノードと関係線が追加される
6. 関係線を選択すると「なぜつながったのか」の AI 説明が出る
7. 元のスクショをいつでも確認できる

この一連の体験がプロダクト価値の中心である。

### 2.2 知識ネットワークビュー(MVP の中心。2D 必須・3D ストレッチ)

ネットワークビューは装飾ではなく中心体験である。**2026-08-15 改訂**: 提出期限(2026-08-21)からの工数逆算により、MVP 必須は **2D 表示**とし、3D 表示は時間に余裕がある場合のストレッチ(Could)とする。目的(簡単に知識を貯め・整理し・視覚的に見やすく・利用しやすい)は 2D 表示でも達成できると判断した。描画には **react-force-graph**(2D/3D 互換 API のライブラリ)を用い、2D 実装を低コストで 3D へ昇格できる形を保つ。MVP で最低限確認できるもの:

- 知識ノード
- ノード間の関係(エッジ)
- ノード選択時: 要約・元スクショ・接続ノード
- エッジ選択時: 関係の種類と AI 説明

見た目の意味づけ(可能な範囲で行う):

- ノードサイズ = 接続数
- 線の太さ = 関連度
- ノード間距離 = 意味的近さ(努力目標)
- 新規追加された関係の強調表示(努力目標)

ノードサイズ・線の太さは F-20 の必須条件、ノード間距離・新規関係の強調は努力目標(Could)であり MVP 完成条件には含めない。ただし複雑な表現よりも「関係の分かりやすさ」を最優先する。**階層構造(球体の自動階層化)・参照頻度の見た目反映は将来構想**とし、MVP には含めない(§2.3)。

### 2.3 将来構想(MVP 完成後)

- URL 取り込み+本文アーカイブ
- 自然文セマンティック検索
- 忘れた頃の再浮上・ダイジェスト・風化と強化
- エンティティ正規化(表記ゆれ吸収)とエンティティページ
- 階層型知識マップの自動構築
- NotebookLM 用プロンプト出力
- 身内公開(利用量上限)
- バッチによる繋がり提案

### 2.4 完成の定義(2段階)

**(a) MVP 完成**(コンテスト・ポートフォリオ提出の到達点):

- [ ] 認証
- [ ] スクショ貼り付け・保存
- [ ] 非同期 AI 解析(タイトル・要約・キーワード/タグ・概念・抽出原文)
- [ ] 関係の生成と説明の永続化
- [ ] ノート詳細と元スクショ確認
- [ ] ネットワーク表示(2D)・ノード選択・エッジ説明確認
- [ ] AI 生成結果の最低限の修正

上記チェックリストは体験の概要であり、正式な MVP 完成条件は §4 の M2 までの全 Must 要件(F-2・F-3・F-4・F-5・F-7・F-19・F-20・F-17(基盤))を満たすこととする。F-21・F-22(2026-08-15 提出スコープ改訂で F-7/F-19 から分割した提出後要件・M3)は **MVP 完成条件に含めない**。

**(b) フル構想完成**: 上記(a)に加えて、正式なフル構想完成条件は §4 の M7 までの全 Must 要件(F-1・F-6・F-8・F-9・F-10・F-11・F-15・F-17・F-18・F-21・F-22 を含む)を満たすこととする。F-12・F-13・F-16 は Could(努力目標)として必須条件から除外する。

(a)(b) いずれの完成判定でも、§5 の非機能要件はその時点で適用可能な項目(MVP 完成なら認可・画像の非公開配信・応答性・数百ノート規模でのグラフ操作性等)を常に満たしていることを条件に含める。

## 4. 機能要件

優先度: **Must**(MVP 完成(§2.4a)またはフル構想完成(§2.4b)の必須条件)/ **Could**(努力目標・任意)。**MS(マイルストーン)列が着手順**を表す。M2 までの Must 要件が MVP 完成の必須条件であり、M3 以降は主にフル構想完成(§2.4b)に向けた要件となる。

### 取り込み(キャプチャ)

| ID | 要件 | 優先度 | MS |
|---|---|---|---|
| F-1 | URL を貼ると、ページ本文を抽出し Claude API で要約・タグ・キーワードを自動生成して保存する。**抽出した本文もアーカイブとして保存し、元記事が消えてもノート内で読める**ようにする(2026-07-10 基準改訂: MVP の中心はスクリーンショット。URL は MVP 外) | Must | M3(将来) |
| F-2 | スクリーンショット画像を貼る/アップロードすると、Claude API のマルチモーダル入力で内容を読み取り、**タイトル・要約・キーワード/タグ・概念(エンティティ)・抽出原文(OCR 相当のテキスト)**を生成して保存する(別途 OCR 不要)。**元画像は必ず保存し**、AI 出力が誤っていても元画像で確認できる。**AI 処理状態(処理中/完了/失敗+失敗理由)をデータとして保持**する。対応画像形式は PNG・JPG・WebP、最大 10MB(デザインハンドオフのバリデーション仕様と一致させる) | Must | M1 |
| F-3 | 手動メモも書ける(貼るだけが主だが、一言添えられる)(M1-2 実装済み) | Must | M1 |
| F-4 | 取り込みは非同期ジョブで処理し、受付は即時応答、処理状況(処理中/完了/失敗)を画面で確認できる。失敗時は再実行できる。AI 解析(F-2)・埋め込み生成(F-7)・関係生成(F-19)は段階を持つパイプラインとして段階別に状態(未処理/処理中/完了/失敗+失敗理由)を管理し、ノート種別ごとに適用する段階を定義し、適用外の段階はスキップとして扱う。ノートの「完了」は適用対象の全段階の完了を指す(手動メモは AI 解析段階を適用外とし、埋め込み生成・関係生成のみ実行する)。部分失敗時は失敗した段階から冪等に再実行できる。段階別状態の詳細設計(画面表示・再実行単位)は M1-3/M1-4 の実装計画で定義する | Must | M1 |

|---|---|---|---|

### 知識ネットワーク(MVP の中心。2D 必須・3D ストレッチ)と将来の構造化

| ID | 要件 | 優先度 | MS |
|---|---|---|---|
| F-20 | **知識ネットワーク(MVP 版)**: ノード=ノート、エッジ=F-19 の関係、のフラットなネットワークを **2D で描画**する(react-force-graph)。パン・ズームができ、ノード選択で要約・ノート種別に応じた内容(スクショノート=元スクショ、メモノート=本文、URL ノート(M3 以降)=アーカイブ本文)・接続ノードを確認、エッジ選択で関係の種類と AI 説明を確認できる。ノードサイズ=接続数、線の太さ=関連度の意味づけを行う。**3D 表示(回転操作を含む)への昇格は Could(ストレッチ。時間余裕時のみ、react-force-graph の 3D コンポーネントへの差し替えで行う)**。ノード間距離=意味的近さ・新規追加関係の強調表示は従来どおり努力目標(Could) | Must | M2 |

## 6. 制約・前提

- DB は MariaDB(ネイティブベクトル対応版。**11.8 LTS を基準とする** — RDS for MariaDB 11.8 の MariaDB Vector 対応を確認済み(2026-08-15。§10-9)。ローカル Docker イメージも M1-4 実装前に 11.8 系へ統一する)。F-7/F-8/F-12 のベクトル検索は MariaDB の VECTOR 型+ベクトルインデックスで実現し、品質に問題が出た場合のみ Qdrant をベクトル専用ストアとして併用する(M0 で技術検証)。ノート間の関係はエッジテーブル(note_relations 相当)で永続化する。階層構造(再帰 CTE)は将来の F-12 で検討。日本語全文検索は InnoDB ngram パーサで実現する

## 9. 技術スタック(決定記録)

**決定(2026-07-07)**: **TypeScript 統一**(バックエンド: Node.js / フロントエンド: React + WebGL)。

**選定理由**(学習コストを除いた保守性・運用性・開発継続性の比較で決定):
- フロントは 3D 脳ビュー(Three.js 系)の都合で React + TypeScript がほぼ確定しており、バックエンドを揃えると型をフロント・バックで共有でき、API 境界の追従漏れをコンパイル時に検出できる(保守性)
- ランタイムが軽く(JVM 比)、Dockerfile・CI・依存管理が1系統で済み、月数十ドル以内のコスト要件に適合(運用性)
- 1機能=「画面+API+ジョブ」を単一言語・単一ツールチェーン(`npm test` / lint 一本)で縦に貫通でき、ハーネスで1機能ずつ回す開発スタイルと相性が最良(開発継続性)
- 重要部品がすべて JS 圏にホームを持つ: 本文抽出 = Mozilla Readability 本家 / Claude 公式 SDK(TS が最も手厚い)/ 非同期ジョブ = BullMQ / 3D = Three.js
- 比較検討した代替案: Spring Boot(既習だが2言語体制の保守・運用コストで劣後)/ Python(クラスタリングは最強だが型と統一性で劣後。F-12 が重くなったら Python ワーカー切り出しの補欠起用余地を残す)/ Go・Rust(このドメインでエコシステムが薄く見送り)

**確定要素**: TypeScript / Node.js / React / MariaDB(ネイティブベクトル。必要時のみ Qdrant 併用 — §6)/ Docker Compose(ローカル)/ AWS は **EC2 + RDS のみ**(EC2 1台に Docker Compose 一式、コスト考慮の決定)/ オブジェクトストレージは MinIO(S3 互換 API、ローカル・本番共通)/ Claude API(公式 TS SDK)

**アプリ構成の決定(2026-07-07)**: **分離型** — Vite + React SPA(web)/ NestJS API(api)/ BullMQ ワーカー(worker)のモノレポ構成。

分離型を選んだ理由(「アプリの目的への適合」で判断):
- 完成系の中心である 3D 脳ビューは SSR 不要の純クライアントアプリであり、Vite SPA なら Three.js 系を回避策なしで扱え、最重要画面の試行錯誤が最速になる(Next.js は `ssr: false` ラップとサーバー/クライアント境界の管理を主要画面で引きずる)
- 裏の主役である AI パイプライン(要約→埋め込み→階層化→関係要約)は、NestJS の BullMQ 統合・スケジューラ・モジュール構造が公式装備で、ジョブの増築に秩序を与える(注: 2026-07-07 時点の決定記録。2026-07-10 基準改訂後の必須パイプラインは「スクショ解析→埋め込み→関連候補探索→関係生成・永続化」であり、階層化は将来の任意拡張(F-12))
- M4 以降複雑化するドメイン(ノート・エンティティ・階層・繋がり・要約キャッシュ)に対し、NestJS の強制的な構造規律が保守性に効く(注: 2026-07-07 時点の決定記録。現行計画では関係の生成・永続化は M1-4、階層は任意の将来要件 — 選定理由としての趣旨は変わらない)
- 型の端から端までの共有は tRPC(スタンドアロンアダプタ)または ts-rest で分離型でも実現できる(方式は M0 で確定)

**M0 で確定した詳細**: ORM = **Drizzle ORM** / 型共有方式 = **ts-rest** / 認証ライブラリ = **`@nestjs/passport` + `passport-jwt`(+ `@nestjs/jwt`)**(この3点の決定理由は docs/adr/0101-orm-and-type-sharing.md 参照)/ モノレポツール = **pnpm workspaces** / テスト・lint ツールチェーン = **Vitest(モノレポ全体で統一)+ ESLint 9(flat config)+ typescript-eslint、フォーマットは Prettier**(この2点は PROJECT.md に決定理由を記載、独立の ADR は無し)。フロント詳細のうち **サーバー状態 = TanStack Query、クライアント状態 = Zustand、ルーティング = React Router、UI = Tailwind は M0 で導入済み**。**グラフライブラリは react-force-graph で決定(2026-08-15。MVP は 2D コンポーネント、3D 昇格時は 3D コンポーネントへ差し替え)**。shadcn/ui は M1-2 で手書き方式により導入済み
